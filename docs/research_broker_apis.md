# U.S. Equity Broker APIs for Day-Trading Platforms — Research Report (2025–2026)

*Compiled August 18, 2026. Sources are official broker documentation, FINRA, and SEC pages. Every factual claim below is followed by an inline citation to the primary source.*

> **Critical regulatory update up front:** The classic Pattern Day Trader (PDT) rule — the $25,000 minimum-equity requirement most trading-platform builders assume is still in force — was **retired by FINRA effective June 4, 2026** and replaced with a new "intraday margin" framework under FINRA Rule 4210(d)(2) ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)). Any architecture built against the old PDT model needs to account for this. Details in Section 3.

## 1. Alpaca Trading API (docs.alpaca.markets)

### 1.1 API structure and authentication

- Alpaca's platform is API-first, offering REST APIs and WebSocket streaming for building trading apps, algorithmic strategies, and brokerage services for equities and crypto ([Alpaca Getting Started docs](https://docs.alpaca.markets/docs/getting-started)).
- Two authentication schemes exist: (1) direct API key/secret pairs (`APCA-API-KEY-ID` / `APCA-API-SECRET-KEY` headers) used for REST and WebSocket connections, and (2) **OAuth2**, intended for third-party applications that let any Alpaca brokerage-account holder connect without sharing their raw API keys ([Alpaca Getting Started docs](https://docs.alpaca.markets/docs/getting-started); [Alpaca WebSocket Streaming docs](https://docs.alpaca.markets/docs/websocket-streaming)).
- For WebSocket auth, the client sends `{"action":"auth","key":"...","secret":"..."}`; for OAuth-based streaming the key is set to the literal string `oauth` and the secret is the OAuth user token (not the client secret) ([Alpaca Streaming Market Data docs](https://docs.alpaca.markets/docs/streaming-market-data)).
- Trading (order/account) WebSocket streaming and market-data WebSocket streaming are separate endpoints and use different frame types: the `trade_updates` stream from the trading WebSocket uses binary frames, while the market-data WebSocket (`wss://data.alpaca.markets/stream` / `wss://stream.data.alpaca.markets`) uses text frames; both support JSON or MessagePack codecs ([Alpaca WebSocket Streaming docs](https://docs.alpaca.markets/docs/websocket-streaming)).

### 1.2 Paper trading environment

- Alpaca's paper trading environment is a **genuinely separate, real-time simulation environment** — orders are never routed to a live exchange; fills are simulated against real-time quotes ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- **Base URL:** `https://paper-api.alpaca.markets` (set via the `APCA_API_BASE_URL` environment variable), versus `https://api.alpaca.markets` for live trading; the API surface/spec is identical between paper and live — only the base URL and API keys differ ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- **Cost:** Free. Anyone globally can create an Alpaca "Paper Only" account by signing up with just an email address — no live/funded brokerage account is required to use paper trading, and no fee is stated for creating or maintaining it ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- The paper account is created with a **default simulated balance of $100,000**; the balance cannot be changed except by deleting and recreating the paper account ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- Paper accounts get **free real-time IEX market data** (same entitlement in paper and live for the free tier) ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- Paper trading supports margin trading, short selling, and premarket/after-hours trading — parity with live, except paper accounts currently do not simulate borrow fees ("Coming Soon") ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- Paper trading does **not** simulate: market impact, information leakage, latency-driven slippage, order-queue position for non-marketable limit orders, price improvement, regulatory fees, or dividends — architects should treat paper P&L as directional, not exact ([Alpaca Paper Trading docs](https://docs.alpaca.markets/docs/paper-trading)).
- Wash-trade protection (see Section 4) applies identically in paper accounts ([Alpaca User Protection docs](https://docs.alpaca.markets/docs/user-protection)).

### 1.3 Supported order types (confirmed current, 2025–2026)

Per Alpaca's official "Placing Orders" documentation, Alpaca currently supports ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)):

| Order type | Notes |
|---|---|
| Market | Fills near-instantly at prevailing price; IPO symbols restricted to limit-only until the first exchange trade |
| Limit | Buy at limit-or-lower / sell at limit-or-higher; sub-penny price increments enforced (2 decimals if price ≥ $1, 4 decimals if < $1) |
| Stop (stop-market) | Converts to a market order once the stop price is touched |
| Stop-limit | Converts to a limit order once the stop price is touched |
| Market-on-Open (MOO) / Limit-on-Open (LOO) | `time_in_force = opg`; only eligible for the opening auction; rejected if submitted 9:28am–7:00pm ET |
| Market-on-Close (MOC) / Limit-on-Close (LOC) | `time_in_force = cls`; only eligible for the closing auction; rejected if submitted 3:50pm–7:00pm ET; `cls` only available on API v2 |
| **Bracket** (`order_class: bracket`) | Entry order + simultaneous take-profit (limit) and stop-loss (stop or stop-limit) child legs; extended hours **not supported**; TIF must be `day` or `gtc` |
| **OCO** ("One-Cancels-Other", `order_class: oco`) | Exit-only pair (take-profit limit + stop-loss stop/stop-limit) attached to an existing position |
| **OTO** ("One-Triggers-Other", `order_class: oto`) | Entry order plus a single attached take-profit *or* stop-loss leg (not both) |
| **Trailing stop** (`type: trailing_stop`) | Dollar (`trail_price`) or percent (`trail_percent`) offset from a continuously updated high-water mark (`hwm`); becomes a market order when triggered; only supported as a standalone order (not yet as the stop-loss leg of a bracket/OCO) |

All confirmed present as of the current docs: market, limit, stop, stop-limit, bracket, OCO, and trailing stop — matching the task's checklist — plus OTO and the opening/closing-auction variants (MOO/LOO/MOC/LOC) ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)).

Time-in-force values: `day`, `gtc`, `opg`, `cls`, `ioc` (Immediate-or-Cancel, API v2 only), `fok` (Fill-or-Kill, API v2 only) ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)).

### 1.4 Extended-hours trading

- Alpaca's API v2 supports order submission and fills during **pre-market (4:00am–9:30am ET) and after-hours (4:00pm–8:00pm ET)**, plus a separate **overnight session (8:00pm–4:00am ET, Sunday–Friday)** as part of Alpaca's "24/5" rollout ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca); [Alpaca 24/5 Trading blog](https://alpaca.markets/blog/introducing-stocks-24_5-overnight-with-alpaca-trading-api)).
- Extended-hours eligibility requires the boolean `extended_hours: true` on the order **and** the order must be a **limit order** with `time_in_force` of `day` or `gtc`; all other order types/TIFs are rejected for extended hours ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)).
- Bracket orders and trailing stops are **not** eligible for extended hours; trailing stops do not trigger outside regular market hours ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)).
- During 24/5 overnight trading, margin buying power is capped at up to 2x (vs. up to 4x intraday during the regular session for PDT-eligible accounts, pre-reform terminology), and the (former) Day Trade Buying Power calculation did not apply overnight ([Alpaca 24/5 Trading blog](https://alpaca.markets/blog/introducing-stocks-24_5-overnight-with-alpaca-trading-api)).
- 24/5 paper trading is also available, using the same endpoints/workflows as live ([Alpaca announcement on X](https://x.com/AlpacaHQ/status/2026674931379921181)).

### 1.5 Rate limits — Trading API and Market Data API

- Trading API: **200 requests per minute per account** ("throttled"); exceeding it returns HTTP 429 ([Alpaca support page: usage limit for API calls](https://alpaca.markets/support/usage-limit-api-calls)).
- Market Data API: **200 requests/minute on the free Basic plan**, up to **10,000 requests/minute** on the paid "Algo Trader Plus" plan; the free plan headline is also advertised as "up to 10,000 API calls/min" on the marketing page but the plan-comparison table specifically lists 200/min (free) vs. unlimited (paid) ([Alpaca Market Data plans page](https://alpaca.markets/data)).
- WebSocket connection/symbol limits differ by plan: the free plan is capped at **30 symbols** on market-data WebSocket streams, while Algo Trader Plus allows **unlimited symbols**; separately, most streaming subscriptions (including no-subscription users) are limited to **1 concurrent connection** per endpoint — a second connection attempt returns error code 406 "connection limit exceeded" ([Alpaca Market Data plans page](https://alpaca.markets/data); [Alpaca Streaming Market Data docs](https://docs.alpaca.markets/docs/streaming-market-data)).

- Alpaca's docs do not use the terms "SIP" explicitly on the pricing page, but functionally the free tier is IEX-only (non-consolidated single-exchange feed) and the paid tier is "All US Exchanges" (i.e., consolidated/SIP-equivalent coverage) ([Alpaca Market Data plans page](https://alpaca.markets/data)).
- For options specifically, Alpaca offers a free "Indicative Pricing Feed" (a derivative of OPRA, not the real quotes) versus the paid, subscription-gated real **OPRA** consolidated BBO feed ([Alpaca Historical Option Data docs](https://docs.alpaca.markets/us/docs/historical-option-data)).
- WebSocket market-data streaming supports channels for **trades, quotes, bars, updated bars, daily bars, statuses, LULDs, corrections, and cancel-errors**, across stocks, crypto, options, and news; the general connection format is `wss://stream.data.alpaca.markets/{version}/{feed}`, with a sandbox equivalent at `wss://stream.data.sandbox.alpaca.markets/{version}/{feed}` and an always-available test stream at `wss://stream.data.alpaca.markets/v2/test` using the fake ticker `FAKEPACA` ([Alpaca Streaming Market Data docs](https://docs.alpaca.markets/docs/streaming-market-data)).

### 1.7 Day-trading-specific restrictions Alpaca enforces

- **As of June 4, 2026, Alpaca has fully retired the PDT rule and its associated restrictions** (PDT designation, $25,000 equity floor, day-trade counting, Day Trade Buying Power) from both its Trading API and Broker API, in line with FINRA's rule change ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)). See Section 3 for full regulatory detail.
- Alpaca replaced Day Trade Buying Power (DTBP) with **Intraday Buying Power** — a continuously updated measure of available margin based on equity, positions, and intraday P&L — and replaced Day Trade Margin Calls with **Intraday Margin Calls / Intraday Margin Deficit (IMD) Calls** ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)).
- The minimum equity requirement for **4x intraday buying power** in leverage-enabled accounts was lowered from the old $25,000 PDT threshold to **$2,000** ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)).
- Legacy account/API fields (`pattern_day_trader`, `daytrade_count`, `last_daytrade_count`, `daytrading_buying_power`, `last_daytrading_buying_power`) were frozen to placeholder values (e.g., `pattern_day_trader: false`) after June 4, 2026 and scheduled for **complete removal from the API by July 6, 2026**; integrators are told to migrate to the `buying_power` field ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)).
- Repeated failure to satisfy an intraday margin deficit within 5 business days can trigger a **90-calendar-day restriction** preventing new/increased short positions or debit balances — this mirrors, but is calculated differently from, the old PDT 90-day cash-restriction ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)).
- Separate from day-trading rules, Alpaca enforces general margin eligibility: accounts need **$2,000+ equity** for margin/short-selling access at all (Reg T minimum); below that, accounts are restricted to 1x (cash) buying power; margin accounts get up to 2x overnight buying power and up to 4x intraday buying power under Reg T ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling)).
- Alpaca applies automated **wash-trade protection**: any order pair that could interact as a same-side buy/sell within the wash-trade rules is rejected with HTTP 403; bracket, OCO, and trailing-stop orders are structurally exempt from this check because Alpaca recognizes them as a linked group ([Alpaca User Protection docs](https://docs.alpaca.markets/docs/user-protection)).

### 1.8 Order status fields and streaming trade updates

- Order `status` field values (per the REST order object and WebSocket `trade_updates` stream) include, as common states: `new`, `partially_filled`, `filled`, `done_for_day`, `canceled`, `expired`, `replaced`, `pending_cancel`, `pending_replace`; and as rare states: `accepted`, `pending_new`, `accepted_for_bidding`, `stopped`, `rejected`, `suspended`, `calculated` ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca)).
- Alpaca's WebSocket `trade_updates` stream (subscribe via `{"action":"listen","data":{"streams":["trade_updates"]}}`) pushes real-time order/execution lifecycle events — `new`, `fill`, `partial_fill`, `canceled`, `expired`, `done_for_day`, `replaced`, plus rarer events (`accepted`, `rejected`, `pending_new`, `stopped`, `pending_cancel`, `pending_replace`, `calculated`, `suspended`, `order_replace_rejected`, `order_cancel_rejected`) — each message embeds the full order object plus event-specific fields like `price`, `qty`, and `position_qty` ([Alpaca WebSocket Streaming docs](https://docs.alpaca.markets/docs/websocket-streaming)).
- There is no separate outbound "webhook" mechanism documented; trade/order updates are delivered exclusively via the authenticated WebSocket stream, which multileg options fills also support with a `legs` array for parent/child order details ([Alpaca WebSocket Streaming docs](https://docs.alpaca.markets/docs/websocket-streaming)).

### 1.9 Notable API changes / new features in the last ~12 months

- **PDT rule retirement and Intraday Margin Framework** — effective June 4, 2026, with legacy fields removed from the API by July 6, 2026 ([Alpaca blog: FINRA Retires the PDT Rule](https://alpaca.markets/blog/finra-retires-the-pdt-rule-introducing-alpacas-new-intraday-margin-framework/)).
- **24/5 trading** (overnight session 8:00pm–4:00am ET, Sun–Fri) rolled out for Trading API users, then extended to Broker API partners, then to 24/5 paper trading ([Alpaca 24/5 Trading blog](https://alpaca.markets/blog/introducing-stocks-24_5-overnight-with-alpaca-trading-api); [Alpaca 24/5 Broker API blog](https://alpaca.markets/blog/alpaca-launches-24-5-trading-for-broker-api-helping-deliver-global-access-to-us-markets/)).
- **Options trading** launched on the Trading API (2024) with Level 1–2 support, then **Level 3 multi-leg options** (spreads, straddles, condors) added in 2025 ([Alpaca 2025 in Review blog](https://alpaca.markets/blog/alpacas-2025-in-review/); [Alpaca Options Trading docs](https://docs.alpaca.markets/us/docs/options-trading)).
- **Hard-to-Borrow (HTB) short-selling / Locates API**, enabling programmatic quote-preview, locate-request, and locate-tracking workflows for shorting HTB securities ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling); [Alpaca HTB announcement on X](https://x.com/AlpacaHQ/status/2069782606191726831)).
- Other 2025 additions per Alpaca's year-in-review: Instant Tokenization Network, Fully-Paid Securities Lending, Fixed Income access, an MCP server for AI-agent integration, OmniSub sub-accounting, and Shariah-compliant investing support ([Alpaca 2025 in Review blog](https://alpaca.markets/blog/alpacas-2025-in-review/)).
- TradingView integration expanded to support options trading directly through TradingView's charting UI using an Alpaca account ([Alpaca on X — TradingView options integration](https://x.com/AlpacaHQ/status/1983171904245846083)).

## 2. Interactive Brokers (IBKR) API options

IBKR offers three distinct API surfaces: **TWS API**, **Client Portal Web API** (aka "Web API"), and **FIX API** ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).

### 2.1 TWS API

- A **TCP socket protocol** API that requires connectivity to a running **Trader Workstation (TWS)** desktop application or **IB Gateway** process; official client libraries exist for Python, Java, C++, C#, and Visual Basic, and the protocol itself can be re-implemented in any language ([IBKR TWS API Documentation](https://www.interactivebrokers.com/campus/ibkr-api-page/twsapi-doc/)).
- The latest version is released as **open source under the GPL license** ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).
- **Rate limits (pacing):** the maximum request rate equals (Maximum Market Data Lines) ÷ 2 per second. Default accounts have 100 market data lines → **50 requests/second**; accounts that increase market data lines (via commissions or a paid "Quote Booster") get proportionally higher throughput, e.g., 200 lines → 100 req/sec ([IBKR Pacing Limitations docs](https://www.interactivebrokers.com/docs/tws-api/doc/pacing-limitations/introduction)).
- Separately, order placement itself is capped by the same ~50 messages/second pacing limit, and IBKR requires monitoring of an "Order Efficiency Ratio"; a maximum of **20 active orders per contract, per side, per account** is enforced ([IBKR TWS API Order Limitations docs](https://interactivebrokers.github.io/tws-api/order_limitations.html)).
- For FIX API users connecting through IB Gateway, the message-rate limit is **250 messages/second**; FIX users **not** going through IB Gateway/TWS have no hard message-rate limit stated, though "less is better" ([IBKR Pacing Limitations docs](https://www.interactivebrokers.com/docs/tws-api/doc/pacing-limitations/introduction)).
- **Running process required:** Yes — the TWS API is explicitly built on a live TCP socket connection to either TWS or IB Gateway; there is no headless/serverless mode ([IBKR TWS API Documentation](https://www.interactivebrokers.com/campus/ibkr-api-page/twsapi-doc/)).
- **Setup complexity:** IBKR states the TWS API is "aimed at experienced professional developers," requires familiarity with object-oriented programming, and explicitly states IBKR "cannot offer programming consulting" — users are pointed to sample Testbed projects (Java, VB, C#, C++, Python) bundled in the install directory ([IBKR TWS API Documentation](https://www.interactivebrokers.com/campus/ibkr-api-page/twsapi-doc/)).

### 2.2 Client Portal Web API ("Web API")

- A modern **REST API + WebSocket streaming** interface covering account opening/management, funding, banking, reporting, and trading, including individual accounts and multi-account/sub-account structures for advisors ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).
- **Running process required:** For retail/individual users, yes — a local Java-based **Client Portal Gateway** process (`clientportal.gw`) must be running (requires a JRE) and the user must authenticate through a browser at `https://localhost:5000`; institutional clients can instead use full OAuth 2.0 (with `private_key_jwt` client authentication) without running a local gateway ([IBKR Launching and Authenticating the Gateway lesson](https://www.interactivebrokers.com/campus/trading-lessons/launching-and-authenticating-the-gateway/); [IBKR Trading Web API page](https://www.interactivebrokers.com/campus/ibkr-api-page/web-api-trading/)).
- **Rate limit:** **10 requests per second** per authenticated username/session, globally enforced ([IBKR Trading Web API page](https://www.interactivebrokers.com/campus/ibkr-api-page/web-api-trading/)).
- **Session behavior:** a brokerage session can remain authenticated for up to 24 hours (resetting at midnight in NY/Zug/Hong Kong time) but the *session itself* times out after ~5 minutes of inactivity unless the client calls a `/tickle` keep-alive endpoint (recommended every ~1 minute); a single username can only have **one active brokerage session** across all IBKR platforms (TWS, Client Portal, mobile) at a time ([IBKR Authentication FAQ](https://www.interactivebrokers.com/docs/web-api/authentication/faq); [IBKR Trading Web API page](https://www.interactivebrokers.com/campus/ibkr-api-page/web-api-trading/)).
- **Paper trading:** Supported — the Client Portal Gateway can authenticate against a separate Paper Trading username/password generated in Client Portal settings, and paper accounts come **pre-funded with $1,000,000 in simulated buying power** ([IBKR: How to Open an IBKR Paper Trading Account](https://www.interactivebrokers.com/campus/trading-lessons/how-to-open-an-ibkr-paper-trading-account/)).
- **Prerequisite:** IBKR only grants access to paper trading (and to any of its APIs) after the user has opened — and had approved — a **live IBKR account**; the live account does not need to be funded immediately, but it must exist and be approved first ([IBKR: How to Open an IBKR Paper Trading Account](https://www.interactivebrokers.com/campus/trading-lessons/how-to-open-an-ibkr-paper-trading-account/)). Additionally, Web API/REST access requires an **IBKR Pro** account — IBKR Lite (commission-free) accounts are explicitly **not supported** ([IBKR: Authenticating with the Client Portal REST API](https://www.interactivebrokers.com/campus/traders-insight/authenticating-with-the-ibkr-client-portal-rest-api/)).

### 2.3 FIX API

- Positioned for **institutions** building high-speed, high-volume order-routing systems with access to broad market depth; connectivity is via **VPN, extranet, leased line, or cross-connect** rather than a simple internet REST/WebSocket call ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).
- Message-rate limit is **250 messages/second** when routed through IB Gateway; standalone FIX connections outside Gateway/TWS have no stated hard limit ([IBKR Pacing Limitations docs](https://www.interactivebrokers.com/docs/tws-api/doc/pacing-limitations/introduction)).
- Paper trading availability and specific order-type support are not detailed on IBKR's public FIX overview page; the primary use case described is institutional "trading at scale" rather than retail day trading ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).

### 2.4 IBKR order types

- IBKR's general marketing page states its APIs can "programmatically place orders, including advanced order types and algos" across all three API surfaces, but does not enumerate the full order-type list on that page, nor on the dedicated market-data pricing page ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php); [IBKR Market Data Pricing page](https://www.interactivebrokers.com/en/pricing/market-data-pricing.php)).
- For **overnight trading specifically**, IBKR currently supports only **Limit and Adaptive Limit** order types — no GTC, no market orders — with two overnight-specific time-in-force choices, `OVERNIGHT` (expires at session end, 3:50am ET) and `OVERNIGHT + DAY` (continues into the next regular session) ([IBKR Overnight Trading Using the Adaptive Algorithm](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-using-the-adaptive-algorithm/); [IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)).

### 2.5 Extended-hours and overnight trading

- IBKR offers **overnight trading for 10,000+ US-listed stocks and ETFs**, from **8:00pm ET to 3:50am ET**, running Sunday evening through Friday morning, accessible via TWS, Client Portal, and Mobile TWS ([IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)); combined with standard extended hours, IBKR advertises **~24 hours/day, 5 days/week** access to US equities and ETFs, with only a 10-minute gap (3:50–4:00am ET) ([IBKR Overnight Trading page](https://www.interactivebrokers.com/en/trading/us-overnight-trading.php)).
- Overnight trades are routed to a distinct venue set — IBKR's own **IBEOS** venue or the combined **OVERNIGHT** venue (internal + external liquidity via partner **Blue Ocean**) — and are treated as an independent venue from regular/extended-hours orders ([IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)).
- Market data for overnight trading is provided **free**, and existing standard US stock trading permissions are sufficient — no separate account-wide setting is required to enable overnight trading ([IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)).
- GTC orders are **not supported** overnight — unfilled orders expire at session end ([IBKR Toolbox: Trading Overnight](https://www.interactivebrokers.com/campus/traders-insight/ibkr-toolbox-trading-overnight-at-interactive-brokers-using-the-trader-workstation/)).
- Options are also tradable during the overnight session ([IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)).
- Trades executed 8:00pm–12:00am ET carry the **following day's** trade date, a consideration for settlement/tax logic ([IBKR Overnight Trading page](https://www.interactivebrokers.com/en/trading/us-overnight-trading.php)).
- Beyond equities, IBKR offers near-round-the-clock access to Cboe/CME equity-index futures and options and to Korea Stock Exchange futures/options during their respective overnight windows ([IBKR Overnight Trading page](https://www.interactivebrokers.com/en/trading/us-overnight-trading.php)).

### 2.6 Market data subscriptions/licensing and costs

- IBKR includes **free real-time streaming data on US-listed stocks/ETFs from Cboe One and IEX** (non-consolidated — i.e., not the full NBBO/SIP) plus up to **100 free snapshot quotes/month**; delayed data is provided free elsewhere it's available ([IBKR Market Data Pricing page](https://www.interactivebrokers.com/en/pricing/market-data-pricing.php)).

## 3. FINRA/SEC Pattern Day Trader (PDT) Rule — current status as of 2025/2026

### 3.1 The rule as it existed through June 3, 2026

- FINRA defined a **pattern day trader** as any customer who executes **four or more "day trades" within five business days**, provided those day trades represent **more than 6% of the customer's total trades in the margin account** over that same 5-business-day window; a broker-dealer could also proactively designate a customer as a PDT if it "knows or has a reasonable basis to believe" the customer will day trade (e.g., after providing day-trading training) ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf)).
- A **"day trade"** was defined as the purchase and sale, or sale and purchase, of the **same security on the same day in a margin account** — including options and short-sale-then-cover round trips; overnight-held long or short positions closed the *next* day (before any new same-day purchase/sale of that security) were **not** day trades ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf)).
- **Minimum equity requirement: $25,000**, which had to be deposited *before* day trading and maintained at all times; each day-trading account had to independently meet this — cross-guaranteeing separate accounts was not permitted ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf)).
- **Consequences:** if equity fell below $25,000, day trading was prohibited until restored; PDT day-trading buying power was capped at **4x** the prior day's maintenance-margin excess; exceeding that limit triggered a day-trading margin call with **5 business days** to meet it (during which buying power dropped to 2x); failure to meet the call by the 5th business day resulted in a **90-day, cash-only restriction** ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf)).
- Brokers were permitted to impose **stricter** rules than the FINRA minimum (higher equity floors, lower buying-power multiples, broader PDT definitions) ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf)).

### 3.2 Does this still apply as of 2025/2026? — **No, as of June 4, 2026, it has been replaced**

- FINRA adopted amendments to **Rule 4210** that **eliminate the PDT day-trade-count designation and the $25,000 minimum-equity requirement in their entirety**, replacing them with a new **"intraday margin" framework** under new Rule 4210(d)(2); the SEC approved the change (Release No. 105226, April 14, 2026), and FINRA set the **effective date as June 4, 2026**, 45 days after publication of Regulatory Notice 26-10 ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).
- Firms were permitted an **18-month phase-in**, with a final implementation deadline of **October 20, 2027**, for those needing more time ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).
- Under the new rule, each firm must calculate an **"intraday margin deficit"** for covered margin accounts (excluding good-faith and portfolio-margin accounts) on any day with an "IML-reducing transaction" (broadly, short sales or purchases that reduce withdrawable margin); this deficit must be **satisfied as promptly as possible**, and remains outstanding until satisfied or **15 business days** pass ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).
- If a customer habitually fails to satisfy intraday margin deficits and misses the **5th-business-day** deadline, the firm must impose a **90-calendar-day restriction** against creating/increasing short positions or debit balances — functionally similar in spirit to the old 90-day PDT freeze, but triggered by margin-deficit behavior rather than day-trade counts ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).
- Regular (non-day-trading) maintenance margin requirements are **unchanged** — the new rule supplements rather than replaces them ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).
- **Architectural implication:** platforms built in 2025 or earlier that gate order flow on `pattern_day_trader` flags, day-trade counters, or a hard $25,000 equity check are now building against a retired rule; new platforms should design around ongoing/real-time margin-deficit monitoring (a running buying-power calculation) instead of a static day-trade counter.

### 3.3 Cash-account alternative and T+1 settlement considerations

- The PDT day-trading buying-power rules apply specifically to **margin accounts**; cash accounts were never subject to the PDT day-trade-count/$25,000 rule, but they are separately constrained by **Regulation T** and **FINRA Rule 4210(f)(9)**'s **"free-riding" prohibition**: a customer may not buy a security in a cash account and pay for it using the proceeds of selling that same security before payment settles ([FINRA Rule 4210 rulebook](https://www.finra.org/rules-guidance/rulebooks/finra-rules/4210); [Federal Reserve — Board Rulings and Staff Opinions on Regulation T](https://www.federalreserve.gov/frrs/regulations/board-rulings-and-staff-opinions-interpreting-regulation-t.htm)).
- A cash account **can** be used for same-day round trips only if it holds sufficient **settled funds** to cover the full purchase; day trading without sufficient settled cash constitutes free-riding ([Federal Reserve — Board Rulings and Staff Opinions on Regulation T](https://www.federalreserve.gov/frrs/regulations/board-rulings-and-staff-opinions-interpreting-regulation-t.htm)).
- A free-riding violation triggers an immediate **90-calendar-day, cash-up-front restriction**, during which every new purchase must be fully funded with settled cash on the trade date ([Fidelity: Avoiding Cash Account Trading Violations](https://www.fidelity.com/learning-center/trading-investing/trading/avoiding-cash-trading-violations); [Federal Reserve — Board Rulings and Staff Opinions on Regulation T](https://www.federalreserve.gov/frrs/regulations/board-rulings-and-staff-opinions-interpreting-regulation-t.htm)).
- The U.S. securities market moved from **T+2 to T+1 standard settlement** effective **May 28, 2024** (SEC Rule 15c6-1 amendment) ([SEC Press Release 2024-62](https://www.sec.gov/newsroom/press-releases/2024-62); [SEC T+1 FAQ](https://www.sec.gov/exams/educationhelpguidesfaqs/t1-faq)). T+1 shortens (but does not eliminate) the practical window during which cash-account day traders must wait for funds to settle before re-using them without risking a free-riding violation — it makes rapid reuse of cash-account capital somewhat faster than under the old T+2/T+3 regime, but does not create a formal "cash-account day-trading exemption"; the SEC's own T+1 FAQ page explicitly does not address cash accounts, PDT, or free-riding, confirming these remain governed separately by Regulation T and FINRA Rule 4210 ([SEC T+1 FAQ](https://www.sec.gov/exams/educationhelpguidesfaqs/t1-faq)).
- **How brokers implement all this:** broker-dealers are required by FINRA rules to determine PDT-style day-trade counts (historically) or now intraday margin deficits (currently) themselves, apply the applicable equity/margin thresholds, issue margin calls, and enforce the resulting trading restrictions — brokers may also impose stricter house rules than the regulatory minimum ([SEC Investor Bulletin: Margin Rules for Day Trading](https://www.sec.gov/files/daytrading.pdf); [FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10)).

## 4. Broker-specific day-trading/margin rules beyond generic FINRA requirements

### Alpaca
- Margin/short-selling access requires **≥$2,000 account equity**; below that, accounts are capped at 1x (cash-only) buying power — this is a Reg T floor Alpaca applies directly, distinct from (and now more prominent than) the old PDT threshold ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling)).
- Alpaca applies its own **overnight-margin-maintenance schedule** tiered by share price and product type (e.g., long positions priced under $2.50 require 100% maintenance margin; over $6.00 require 30%; 2x leveraged ETFs require 50%; 3x leveraged ETFs require 75%; short positions require the greater of a flat per-share amount or a percentage) — these are Alpaca house rules layered on top of the FINRA 25% baseline maintenance margin ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling)).
- Alpaca charges tiered **margin interest** (4.75%/year for "Elite" users, 6.25%/year otherwise) on end-of-day debit balances, and separate **stock-borrow fees** for Hard-to-Borrow (HTB) short positions, billed in round lots of 100 shares regardless of actual shares shorted ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling)).
- Alpaca enforces a **concentrated-position margin surcharge**: if a single security exceeds 70% of an account's equity value and the margin balance is ≥$100,000, the maintenance-margin rate on that position rises to 50% ([Alpaca Margin and Short Selling docs](https://docs.alpaca.markets/docs/margin-and-short-selling)).
- Alpaca's **wash-trade protection engine** rejects a broad matrix of same-side order pairs (e.g., a market buy followed by any opposite-side sell order is always rejected) unless structured as a bracket/OCO/trailing-stop, which are explicitly exempted ([Alpaca User Protection docs](https://docs.alpaca.markets/docs/user-protection)).

### Interactive Brokers
- IBKR requires margin/short-selling clients to be on **IBKR Pro** (not Lite) and to have a fully **funded, approved live account** before any API-based margin trading, paper trading, or short selling is possible — a stricter gating step than Alpaca's model ([IBKR: Authenticating with the Client Portal REST API](https://www.interactivebrokers.com/campus/traders-insight/authenticating-with-the-ibkr-client-portal-rest-api/); [IBKR: How to Open an IBKR Paper Trading Account](https://www.interactivebrokers.com/campus/trading-lessons/how-to-open-an-ibkr-paper-trading-account/)).
- During IBKR's overnight session, only **Limit and Adaptive Limit orders** are permitted (no market orders, no GTC) — a broker-specific liquidity-driven restriction beyond generic FINRA rules ([IBKR Overnight Trading Using the Adaptive Algorithm](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-using-the-adaptive-algorithm/)).
- IBKR treats overnight venue routing (IBEOS / OVERNIGHT) as an **independent venue** from regular/extended-hours order flow, with its own trade-date conventions for trades executed 8:00pm–midnight ET ([IBKR Overnight Trading in TWS](https://www.interactivebrokers.com/campus/trading-lessons/overnight-trading-in-tws/)).
- IBKR's TWS API imposes a house-level **20-active-orders-per-contract-per-side-per-account** cap and requires monitoring of an internally defined "Order Efficiency Ratio" — an operational constraint specific to IBKR, not a FINRA/SEC requirement ([IBKR TWS API Order Limitations docs](https://interactivebrokers.github.io/tws-api/order_limitations.html)).

## 5. General notes: order types, market-data licensing, and streaming across both brokers

- **Order-type breadth:** Alpaca's order-type set (market, limit, stop, stop-limit, MOO/LOO, MOC/LOC, bracket, OCO, OTO, trailing stop) is fully enumerated and documented in a single reference page, whereas IBKR advertises "access to IBKR's entire suite of order types" and "advanced order types and algos" across its APIs without a single authoritative public enumeration on its top-level API page — IBKR is understood in the industry to support a much larger catalog of algorithmic/conditional order types (e.g., via its "Algos" library) than Alpaca, but the exact current list is not published on the compared pages, so specific claims beyond what's cited above should be verified against IBKR's order-types reference before implementation ([Alpaca Orders at Alpaca docs](https://docs.alpaca.markets/docs/orders-at-alpaca); [IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).
- **Market-data licensing model — SIP/consolidated fees and redistribution:** Consolidated U.S. equity market data (the "SIP" feed, formally the Consolidated Tapes A/B/C data) is licensed through national market system plans; fee schedules and redistribution-fee policy are governed by SEC rules under Regulation NMS, and redistribution fees historically apply to vendors/consolidators that redistribute SIP data to third parties, while self-aggregators using data only internally are not subject to those redistribution fees ([SEC Final Rule: Market Data Infrastructure](https://www.sec.gov/files/rules/final/2020/34-90610.pdf); [FINRA comment letter on SIP/MDI fees](https://www.finra.org/sites/default/files/2021-12/finra-comment-letter-12-17-2021-s7-24-89-SIP-MDI-Fees-1.pdf)). This is the underlying regulatory reason both Alpaca (via its paid "All US Exchanges" tier) and IBKR (via its per-exchange Network A/B/C subscriptions) charge separately for consolidated real-time data instead of bundling it for free — the fees flow back to the exchanges/SIP operators, with the broker/platform retaining a small administrative cut (IBKR states 5–10%) ([IBKR Market Data Pricing page](https://www.interactivebrokers.com/en/pricing/market-data-pricing.php)).
- **Redistribution restrictions in practice:** IBKR's pricing page explicitly distinguishes "Professional" vs. "Non-professional" subscriber classes (tied to SEC/exchange-defined criteria — registration status, employment in financial services, or business use) and charges materially more for professional use, reflecting standard exchange data-redistribution/usage licensing tiers rather than a broker-specific policy ([IBKR Market Data Pricing page](https://www.interactivebrokers.com/en/pricing/market-data-pricing.php)). Alpaca's model is simpler — a flat $99/month unlocks "All US Exchanges" real-time data regardless of professional status, per its published plan comparison ([Alpaca Market Data plans page](https://alpaca.markets/data)) — though builders should confirm current terms directly with Alpaca before redistributing data to end users of a multi-tenant platform, since data-redistribution rights for third-party end users are a distinct licensing question from data *access* rights for a single account.
- **WebSocket/streaming capability comparison:**
  - *Alpaca:* Two separate WebSocket domains — one for **account/order/trade updates** (`trade_updates` stream, binary frames) and one for **market data** (`stream.data.alpaca.markets`, text frames), both supporting JSON or MessagePack, with market-data channels for trades/quotes/bars/updated-bars/daily-bars/statuses/LULDs/corrections/cancel-errors ([Alpaca WebSocket Streaming docs](https://docs.alpaca.markets/docs/websocket-streaming); [Alpaca Streaming Market Data docs](https://docs.alpaca.markets/docs/streaming-market-data)).
  - *IBKR:* The Client Portal Web API offers **WebSocket streaming** for real-time market data and "critical notifications," described only at a high level on IBKR's top-level API page without the same level of publicly documented message-type detail found in Alpaca's docs; the TWS API instead uses a persistent TCP socket connection (not a WebSocket) to push market data and order/execution events to a locally running client ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php); [IBKR TWS API Documentation](https://www.interactivebrokers.com/campus/ibkr-api-page/twsapi-doc/)).
  - Overall, Alpaca's streaming interfaces are simpler, cloud-native, and more thoroughly self-documented for a from-scratch integration; IBKR's are more powerful/global in scope (170 markets, 40 countries per IBKR's page) but assume an on-premises or persistently-running gateway process and more specialized integration effort ([IBKR Trading API Solutions page](https://www.interactivebrokers.com/en/trading/ib-api.php)).
